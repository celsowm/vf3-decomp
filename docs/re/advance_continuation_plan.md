## Batch completion and stop rules

- Aim for family batches of roughly 2,000--5,000 marginal bytes when evidence
  supports them. Smaller complete batches remain useful; never relax proof gates
  to meet a batch size.
- After two justified fixture attempts add no body PCs, park that approach with
  its exact blocker. Resume only with a new runtime contract or scenario.
- Require complete frozen-body development execution, at least 64 distinct
  complete inputs across two scenarios, and strict complete-state replay with
  zero skips. Independent acceptance uses reserved scenarios and changed inputs,
  with pointer relocation where valid. It need not repeat every development PC;
  acceptance evidence must not drive implementation changes.
- Verify targeted roots and affected parents first. Build an immutable executable
  snapshot, bind proofs to its hash, and use `--matrix-executable` for integration.
  Run one full repository regression for each final integration milestone;
  repeat it only after new changes or unresolved failures justify repetition.
- Audit artifact hashes and marginal byte unions, update the ledger and commit
  each accepted milestone. Report gain, readability work, parents unlocked and
  blockers still open.
- Turn new Python analysis into reusable standard-library tools with CLI inputs
  and machine-readable reports. Reuse existing tools; avoid inline Python.
- Keep captures, binaries, build output and original assets out of commits.

Execution begins with A and family ranking; C supplies new scenarios early.
Move into B as shared contracts become clear, and run D only with a bounded,
evidence-backed pilot. Reassess feasibility at every byte checkpoint.
